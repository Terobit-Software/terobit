# terobit pack - .tbpk - v1

## layout

```
[ common header        24 bytes, magic TBPK, version 1 ]
[ table of contents    64 bytes                        ]
[ manifest section     a complete .tbman file          ]
[ signature section    a complete .tbsig file, or empty if unsigned ]
[ index section        postcard IndexV1                ]
[ data section         chunks                          ]
```

sections come in this order, don't overlap, and leave no gaps. the file is exactly
`24 + body_len` bytes, where the body is everything after the common header.

## table of contents

fixed width little endian, right after the [common header](../common/HEADER.md). offsets
are from the start of the file.

| offset | size | type  | field              |
|--------|------|-------|--------------------|
| 24     | 8    | `u64` | `manifest_offset`  |
| 32     | 8    | `u64` | `manifest_len`     |
| 40     | 8    | `u64` | `signature_offset` |
| 48     | 8    | `u64` | `signature_len`    |
| 56     | 8    | `u64` | `index_offset`     |
| 64     | 8    | `u64` | `index_len`        |
| 72     | 8    | `u64` | `data_offset`      |
| 80     | 8    | `u64` | `data_len`         |

the table isn't signed. that's safe because nothing in it is trusted: if it's tampered
with, the signature, the index hash or a chunk hash stops matching.

limits, checked before reading anything:

- `manifest_len` at most 64 mib
- `signature_len` at most 4 kib (0 means unsigned)
- `index_len` equal to the manifest's `index.len` (checked after the manifest is verified)

## index

postcard encoded. its length and hash are in the signed manifest, so the index is fully
trusted once its hash matches.

```rust
struct IndexV1 {
    /// most raw bytes a chunk can hold. 1 mib when written by the v1 tool, readers accept
    /// any power of two from 64 kib to 16 mib
    chunk_size: u32,
    /// in data section order
    chunks: Vec<ChunkEntry>,
    /// same length and order as the manifest's `files`
    files: Vec<FileLocation>,
}

struct ChunkEntry {
    /// where the stored bytes start, from the start of the data section
    offset: u64,
    /// bytes in the data section
    stored_len: u32,
    /// bytes after decompression, 1 to chunk_size
    raw_len: u32,
    compression: Compression,
    /// hash(CHUNK, stored bytes), see integrity
    hash: [u8; 32],
}

enum Compression {
    /// stored bytes are the raw bytes. stored_len equals raw_len
    None = 0,
    /// zstd, version and level pinned by the manifest version
    Zstd = 1,
}

struct FileLocation {
    /// the chunk the file starts in
    first_chunk: u32,
    /// where the file starts in that chunk's raw bytes
    offset_in_chunk: u32,
}
```

a file's bytes are `size` bytes (from the manifest) starting at `offset_in_chunk` in
`first_chunk`. if the file is longer than what's left of that chunk, it continues at the
start of the next chunk, and so on. a file with size 0 has location `0, 0` and reads
no chunks.

readers must reject an index where:

- chunks aren't in ascending offset order, overlap, or run past the data section
- a `None` chunk's `stored_len` isn't its `raw_len`, or a `Zstd` chunk's `stored_len`
  isn't less than its `raw_len`
- a file's range runs past the last chunk
- `files` has a different length than the manifest's `files`

## reading a pack

1. read the common header and table of contents. check the limits
2. read the manifest and signature sections. verify the signature (see
   [tbsig v1](../tbsig/v1.md)), then decode the manifest and check its
   [rules](../tbman/v1.md#rules)
3. if `access` is `Licensed`, check the license (see [tblic](../tblic/REF.md))
4. read the index, check `hash(INDEX, bytes)` against the manifest, then decode and check it

after that, reading a file:

1. find the chunks covering the bytes you want
2. read each chunk's stored bytes with a positional read
3. check `hash(CHUNK, stored bytes)`. stop on mismatch, before decompressing
4. decompress into a buffer of exactly `raw_len` bytes. more or less output is an error,
   so a chunk can never expand past its stated size
5. take the slice you need

## writing chunks

the v1 pack tool chunks files like this, so the same content always produces the same
pack:

1. go through files in manifest order (sorted by path)
2. **large files** (256 kib or more) start a new chunk and fill as many chunks as they need.
   their last chunk isn't shared with anything else
3. **small files** (under 256 kib) go into the currently open small-file chunk. if one
   doesn't fit, that chunk is closed and a new one is started, so a small file never
   spans two chunks
4. the open small-file chunk is closed when the next large file starts and at the end

large files getting their own chunks means an edit to one file only changes that file's
chunks. small files share chunks because compressing a 2 kib file on its own wastes
space and a seek.

then each chunk is compressed with zstd. if that saves less than 20%
(`stored_len * 5 > raw_len * 4`), the chunk is stored uncompressed instead. already
compressed files like `.png`, `.ogg` and `.ktx2` usually end up uncompressed, so loading
them costs no decompression.
